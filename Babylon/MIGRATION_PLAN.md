# Babylon migration plan

## Цель

Создать Babylon.js-реализацию STARFALL, функционально эквивалентную корневой v85, сохранив мир, механику, контент, управление, сохранения и художественную идентичность. После достижения parity — отдельное решение о переводе production.

## Источник истины

- Baseline: `../STARFALL_CURRENT.html`, v85, commit `05c7adb9fcfa8d29ab583c77158853902dc99838`.
- Поведенческие контракты: `../STARFALL_PASSPORT.md`, `../CHANGELOG.md`, корневые тесты.
- Babylon-прототипы из чатов не считать актуальной базой. Их можно использовать только как справочный код после построчного аудита и проверки против v85.

## Архитектурные решения

1. Babylon.js — единственный renderer новой версии.
2. Yuka — высокоуровневый AI/steering; FlightModel остаётся авторитетной динамикой корабля.
3. Havok — collision/physics adapter там, где это необходимо. Не использовать Havok как замену космической инерции.
4. GSAP — UI/cinematic transitions, не игровой timestep.
5. Не подключать Rapier параллельно Havok для одной и той же физики.
6. Сохранять существующие пути ассетов и стабильные ID.
7. Не внедрять Vite/TypeScript до подтверждения необходимости; сначала parity prototype и deployment spike.
8. Точные версии зависимостей фиксировать в package manifest/lockfile и проверять на iOS Safari.

## Контракт этапа

Этап не считается завершённым по наличию функций/классов. Нужны:
- поведенческий тест;
- проверка сохранений;
- отсутствие регрессий в уже перенесённых системах;
- измерения производительности, если затронут рендеринг/симуляция;
- обновлённый локальный changelog и тестовая матрица.

## Правило коммитов

До B7 — изменения кода и документации новой реализации остаются в `Babylon/`. Не менять root game file и GitHub Pages. Один завершённый этап — один коммит в `main`, например `Babylon: B1 — Babylon runtime vertical slice`.
